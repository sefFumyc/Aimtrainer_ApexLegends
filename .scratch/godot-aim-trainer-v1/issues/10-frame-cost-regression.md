# 10 — 主菜单单帧渲染成本回归排查（0.36→0.8ms）

Status: ready-for-agent

## 背景

GPU 占用排查（vsync 失效修复，见 `project.godot` 的 `run/max_fps` 注释）时的附带发现：
主菜单单帧成本在最近 3 个提交间**翻倍**（同机同条件下实测）：

| 提交 | 菜单帧率 | 单帧成本 |
|---|---|---|
| `ec64769`（红屏二轮） | ~2700 fps | ~0.36 ms |
| `bbcb459`（HEAD，曳光飞行弹段） | ~1200 fps | ~0.80 ms |

区间内共 3 个提交：`8f7052a`（出厂默认烘焙 + pose_applied 特效采样）、`0bfa5be`（曳光起点
枪管轴线 + FOV 差补偿）、`bbcb459`（曳光改飞行弹段）。

量级无害：帧率被 vsync/max_fps 封顶后无任何用户可感知影响。本票只为性能卫生，
**不阻塞任何工作**。

## 嫌疑方向（按可能性排序）

1. **曳光段每帧改写 `BoxMesh.size`**（`main.gd _place_tracer_seg`）——菜单态曳光不活跃，
   理论上不该命中菜单成本；但若 mesh 改写触发的缓冲重建有全局副作用，可解释。
2. **`muzzle_reproject.gd` FOV 差补偿**——纯数学，但调用点若被挪进每帧路径（`8f7052a`
   的 pose_applied 改动涉及 main/viewmodel/player 三处接线）可能引入额外矩阵求逆。
3. **`8f7052a` 出厂默认烘焙**——若烘焙 inadvertently 改了渲染相关默认值（画质档、
   阴影参数），首帧起成本即不同。

## 方法建议

`git worktree` 逐提交检出，同条件跑 `--print-fps` 三分钟取稳定段中位数；定位到提交后
用 Godot profiler / 二分注释法定位到函数。注意排查 lesson：跨提交测量需同机同驱动同
shader 缓存状态，首次导入会污染首测。

## 验收

- 定位到具体提交与函数；
- 若修复成本 < 半小时的低风险改动则顺手修，否则记录结论关闭本票。
